# 我们实验的漏洞 / Threats to Validity

一份自觉的自我批评。按「**是否真的威胁结论**」排序,不按好说难说排。
写这份不是为了认错,是因为**审稿人一定会问**,而且有几条我们自己不修就没法站住。

---

## 🔴 严重:直接威胁核心结论

### 1. 机制是**推断**的,不是**直接观测**的

**问题。** 我们说"信号来自 encoder cache",但 **vLLM 0.11.0 根本不暴露 encoder/processor cache 的指标** —— `vllm/v1/metrics/loggers.py` 里搜不到 `mm_cache` / `encoder_cache` / `mm_encoder`(已核实)。所以我们**看不到**"encoder cache 命中了"这件事,只能靠**排除法 + 冲刷实验**推断。

而且源码写明 processor cache *"is duplicated for each API process and engine core process"*(`vllm/config/multimodal.py:46-48`)。**真实缓存拓扑比我们画的"两个格子"更复杂**,我们说"encoder ≈37ms、processor ≈6ms"这个划分**可能过于干净**。

**影响。** 结论方向("有东西没加 salt 在泄露")很稳;但**归因的具体划分**是可质疑的。

**补法。** 给 vLLM 打个小 patch,在 `EncoderCacheManager.check_and_update_cache` 里加计数器或日志,重跑一次。这是唯一能把"推断"变成"观测"的办法。工作量:中。

---

### 2. 几乎所有结论都是**单次运行**,没有 run-to-run 重复

**问题(已解决,保留记录)。** 负载实验曾经显示换一次运行结论会翻转:

| 并发线程 | 第一次运行 | 第二次运行 |
|---|---|---|
| 8 | AUC **0.000**(完美分离) | AUC **0.212**(检不出来) |
| 32 | AUC 0.048 | AUC 0.014 |

同样 8 线程,一次完美、一次失败。**那其他结论凭什么相信?**

严格说,exp3 的**每一条**结论(图像 46.7 ms、音频 48.4 ms、文本 4096 的 492.9 ms)**都只跑过一次**。效应量大的(KS = 1.0)大概率稳,但**我们没有量化证据说明它稳**。

**影响。** 这是对**全部结论可靠性**的一般性威胁,也是最好补的一条。

**✅ 已补(K = 3,每次重启 vLLM 服务器)。** 结果:

| 测量 | 每次的 AUC | 每次的 Δ p50 |
|---|---|---|
| 文本 idle | 0.000, 0.000, 0.000 | 91.5, 92.1, 93.4 ms |
| 文本 8 线程负载 | 0.014, 0.044, 0.043 | 53.4, 53.0, 58.8 ms |
| 文本 salt ON | 0.570, 0.491, 0.514 | −0.4, 0.1, −0.0 ms |
| 图像 salt-ON 攻击 | 0.000 ×3 | 65.3, 65.9, 66.6 ms |
| 图像(同图不同提示词) | 0.000 ×3 | 64.9, 66.8, 66.7 ms |
| 音频 salt-ON 攻击 | 0.000, 0.062, 0.000 | 55.6, 56.2, 59.9 ms |

**汇总(3 次的 mean ± sd)。** 文本 idle:Δ 92.4 ± 1.0 ms, AUC 0.000 ± 0.000, AP 1.000 ± 0.000;文本 8 线程负载:Δ 55.1 ± 3.3 ms, AUC 0.034 ± 0.017, AP 0.971 ± 0.015;文本 salt ON:Δ -0.1 ± 0.3 ms, AUC 0.525 ± 0.041, AP 0.532 ± 0.018;图像 salt-ON 攻击:Δ 65.9 ± 0.7 ms, AUC 0.000 ± 0.000, AP 1.000 ± 0.000;图像(同图不同提示词):Δ 66.1 ± 1.1 ms, AUC 0.000 ± 0.000, AP 1.000 ± 0.000;音频 salt-ON 攻击:Δ 57.2 ± 2.3 ms, AUC 0.021 ± 0.036, AP 0.989 ± 0.019;FLAC 是否复用原始条目:**3/3 全为 False**。

**结论:可分性(AUC/AP)几乎完美可复现;绝对效应量只在同一协议内可复现。**

- 所有头条结论都复现了(图像/音频每次 AUC ≤ 0.062,AP ≥ 0.968)
- **同一个协议内**效应量很稳(图像 65.9 ± 0.7 ms,CV ≈ 1%)
- **跨会话**不稳:图像攻击最早测到 **46.7 ms**,现在 **65.9 ms**,相差 **41%**
- → **效应量必须报区间("约 47–67 ms"),不能报单点。**

**剩下的小问题:** `text_load` 那次 8 线程的 AUC 0.212 现在看是**离群值**(那个协议在一个服务器会话里连续扫了 5 个负载档位)。全部 5 次 8 线程测量:0.000 / 0.212 / 0.014 / 0.044 / 0.043 —— **5 次里 4 次 AUC ≤ 0.044**。

### 3. 恢复实验的 prompt 是**我们为放大信号设计出来的**

**问题。** `text_recovery` 的结构是:

```
HEAD [字段A] 1024个已知token [字段B] 512个已知token [字段C] 256个已知token
```

那三段长已知文本是**人为加的**,目的是让"猜对字段"能把匹配前缀延长 1024 个 token,信号才够大。**真实 system prompt 未必有这么方便的"长已知段"。**

**影响。** 这个实验证明了**协议可行**,但**没有证明它在真实 prompt 上可行**。属于"我们制造了有利条件"。

**补法。** 用一条真实的 system prompt(例如 JSON 格式的客服模板)重做,看信号是否仍足够。工作量:中。

## 🟡 中等:限制可推广性

### 4. 图像用的是**合成噪声图**,不是真实图片

随机噪声改一个像素会剧烈改变视觉特征,真实图片未必。**但这不影响"精确内容"这个结论** —— mm_hash 是精确哈希,改一位就变。

真正缺的是:真实攻击场景里,攻击者预先拥有的是**真实图片**(泄露的截图、人脸、文档)。我们用噪声图验证了机制,但**没有验证这一类**;也没有验证"攻击者手上得有候选图片"这个前提的实际难度。

**补法。** 换成真实图片(公开数据集)COS 一次。成本:低。

### 5. 音频"为什么 FLAC 失败"的解释是**本地推测**

我们说"WAV 与 FLAC 解码出的数组差 3.05e-05",那是**本地用 libsndfile 1.2.2 复现的**。**vLLM 容器里的解码路径**(是否用 librosa、什么 sr/mono/dtype)**没有验证**。方向一致,但解释未被证实。

**补法。** 在容器里直接解码两种格式并 diff 数组。成本:低。

### 6. 只测了 prefix fraction = 1,没测 < 1

我们的文本实验都是"发**一模一样**的 prompt"。**论文的 level 2–4 用的是 0.95**(前 95% 相同、后面不同)。这块我们完全空着。

代码其实已经写好了(`reproduce_gu`,含 fraction 扫描),但**没跑完就停了**。

**补法。** 跑 `reproduce_gu`。成本:低(约 30 分钟 L4)。

### 7. 客户端计时 + localhost,**没测网络抖动**

信号是几十毫秒,localhost RTT 是微秒级所以没事。但**真实跨机房 RTT 是几十毫秒,和信号同量级**。

而负载实验的结论(8–16 线程检不出来)**恰恰暗示真实网络条件下可能失效**。论文用的是从 HTTP header 读服务器端时间(server-side timing),我们没用。

**补法。** 用 vLLM 的 server-side 计时头,或在客户端注入人工延迟/抖动。成本:中。

### 8. 单模型、单配置

文本只有 Qwen2.5-3B,图像只有 Qwen2.5-VL-3B,音频只有 Qwen2-Audio-7B,`block_size` 固定 16。

**换个视觉编码器架构,"encoder cache 存在与否"可能就不同** —— 并非所有 VLM 在 vLLM 里都走同一个 `EncoderCacheManager` 路径。这个我们没验证。

**补法。** 第二个 VLM(如 LLaVA 系)重复图像实验。成本:中。

### 9. 多重比较**没做校正**

我们算了几十个 KS / AUC / AP。论文用 Bonferroni(÷3、÷2)。**我们没校正。** 主结论效应量巨大(KS = 1.0)不受影响,但边缘那些(AUC 0.2–0.6、p = 0.006 的)本来就不该单独下结论。

**补法。** 在 `analyze_rigor.py` 里加 Bonferroni / BH-FDR。成本:低(纯重算)。

### 10. 机制实验的配置和主实验**不同**

`mm_mechanism` / `mm_evict` 加了 `--max-num-batched-tokens 2048`(为了能冲掉 encoder cache),**和主实验 `mm` 的默认配置不一样**。跨实验比较时不严格。

## 🟢 小的 / 已处理的,但要知道

### 11. `mm_evict` 的决定性对照只有 3 个数字

before / after / control **各探一次**,不是分布。效应很大(37.4 → 0.37 ms)所以可信,但严格说是**单点测量**。

### 12. 1 像素实验 n=15,是 **null result**

AUC 置信区间包含 0.5 **不等于证明没有效应**,只是没检出。文档里已改成"上界 ~1.7 ms"(正确),但只扫了**一个像素位置、一个通道、15 次**。没有扫位置和幅度。

### 13. 没有测 `cache_salt` 的**部署现实**

我们是手动传不同 salt。真实部署里 salt 怎么生成、多久轮换?**如果默认根本不开 `cache_salt`,那"防御不完整"就变成"防御根本没开"** —— 那是另一个(可能更严重的)故事。这个完全没测。

### 14. 没实现修复

论点停在"这里有个洞",没到"这样补上就好"。

### 15. 那三个"假泄露"陷阱 —— 说明这类实验的默认失败模式就是**假阳性**

我们踩了才发现:共享 template block、没预热攻击者 salt、攻击者命中自己缓存。反过来说:**如果没踩到,我们就会发表一个错的结果。** 这值得写进论文,但也说明**这个领域的负面结果特别不可信**。

## 答辩时怎么处理

**主动说,别等被问。** 标准做法是单独一页 "Threats to Validity",把这页里 🔴 的三条放上去,并说清"我们知道 + 这是我们计划怎么补"。

**最该练的一句话:**

> 我们的机制是**推断**出来的而不是直接观测到的(因为 vLLM 不暴露这两个缓存的指标),但我们用两组独立对照把其他解释都排除掉了;下一步是给 vLLM 打 patch 拿直接证据。

**不要说的:**

- ❌ "我们证明了 encoder cache 是唯一原因" —— 我们只排除到"只剩它",而且 processor cache 的贡献还占约 6 ms。
- ❌ "攻击在真实网络下可用" —— 没测,而且负载实验的结果提示可能不可用。
- ❌ "我们复现了那篇论文" —— 复现是队友做的。
