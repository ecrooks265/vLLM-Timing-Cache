# 最重要的发现(中文,给人看的版本)

> 技术细节和英文正式版在 `FINDINGS.md`;这一份是**看懂用**的。
> 一句话:**vLLM 有个专门防这类攻击的功能叫 `cache_salt`,对文字有用,对图片没用。**

---

## 1. 先说清我们在做什么

课程要求:先复现那篇论文,再在它基础上扩展。

- **复现** = 队友在做(Gu et al., *Auditing Prompt Caching in Language Model APIs*, ICML 2025)。那篇论文是去**审计 17 家商业 API**(OpenAI、Anthropic……),看它们有没有在用户之间共享缓存。
- **我们** = **扩展那一半**。我们用**真的 vLLM 0.11.0**(官方 PyPI 包,官方 `vllm serve` 命令,真 GPU 上的真模型),去测它**没测过的东西**。

**我们和论文的接口在这里:** 论文 §6 提了四条缓解措施,**一条都没实测**。第一条是 *"only per-user caching should be allowed"*(只允许每用户独立缓存)。**vLLM 的 `cache_salt` 就是这条措施的生产实现**——它自己的源码里写着,这个参数是用来 *"prevent an attacker to guess prompts in multi-user environments"*。

**所以我们的工作就是:第一个去测这条缓解措施到底管不管用、代价多大。**

---

## 2. 这个攻击到底是怎么回事(用厨房打比方)

想象一个**大厨房,很多租户共用**:

- 有人做了一道菜,厨房把半成品留着 → 下一个人做同样的菜**就快**。
- **快多少本身就是情报**:你只要掐表,就知道"有人做过这道菜"。
- 在 LLM 里,这个"快"是 **TTFT(从发出请求到收到第一个字的时间)**。掐表不需要任何特权,一个普通 API 用户就能做。

`cache_salt` 的防御思路:给每个租户一个**私人标签**,你做的菜放你自己标签的格子里,别人拿不到。

**这个思路对文字是对的。** 我们实测:加了 salt 之后,攻击者的探测和"探测一个从没人发过的东西"在统计上**完全无法区分**。

---

## 3. 问题出在哪:一张图片要经过三个格子

| 格子 | 里面装什么 | `cache_salt` 加标签了吗 |
|---|---|---|
| 1. 文字菜谱筐(KV 前缀缓存) | 提示词的 token | ✅ **加了** |
| 2. 切菜台(图片预处理缓存) | 解码/缩放/归一化后的图 | ❌ **没加** |
| 3. 炒菜锅(视觉编码器缓存) | 跑完视觉模型的结果(最贵的一步) | ❌ **没加** |

格子 2 和 3 是**按图片内容本身**做索引的,**跟 salt 完全无关**。所以攻击者端上同一张图,厨房一看:"这菜我切过了、炒过了" → **照样快**。

---

## 4. 三个数字,这就是全部证据

受害者发一张图 → 攻击者发**同一张图**(但用自己的 salt):

| 攻击者发的是 | 攻击者花的时间 |
|---|---|
| 受害者发过的那张图 | **39.1 毫秒** |
| 一个从没人发过的图 | **85.9 毫秒** |

**差 46.7 毫秒,统计上零重叠(KS = 1.000,AUC = 0.000)** —— 意思是攻击者**100% 能分出来**,不会误判。

音频一样:**40.4 vs 88.8 毫秒,差 48.4 毫秒**。

### 为什么我们确定不是测量误差

我们读的是 **vLLM 引擎自己的计数器**(`vllm:prefix_cache_hits` / `vllm:prefix_cache_queries`)。上面这两次请求:

**文字缓存命中量完全一样,都是 16 个 token。**

也就是说——**第 1 个格子确实被锁住了**。如果泄露来自文字缓存,这两次应该一样快才对。它们差了 47 毫秒,所以泄露**只可能来自格子 2 和 3**。

这是这个结论最有力的地方:**我们自己把"是文字缓存泄露"这个解释排除掉了。**

### 比听起来还糟

攻击者**甚至不需要知道受害者写了什么提示词**:

| | 时间 |
|---|---|
| 受害者的图 + 攻击者**自己随便写的**提示词 | **31.2 毫秒** |
| 陌生图 + 同一个提示词 | 61.4 毫秒 |

差 30.2 毫秒,而且这两次的文字缓存命中量**都是 0**。文字信道需要猜对整段前缀,**图片信道只要那张图**。

---

## 5. 我们怎么证明"就是格子 3"

光说"应该是编码器缓存"不够,所以做了三组对照实验:

| 实验 | 结果 | 结论 |
|---|---|---|
| 正常设置 | 优势 42.5 毫秒 | 有泄露 |
| **关掉格子 2**(`--mm-processor-cache-gb 0`) | 优势 **41.1 毫秒,基本没变** | 不是格子 2 的锅 |
| 往格子里灌 400 / 1200 张不同的图 | 优势降到 7.2 / 6.4 毫秒,**卡在 22% 不降了** | 说明还有第二个格子冲不掉(格子 2 有 4 GB,太大) |
| **关格子 2 + 灌爆格子 3** | 优势 **37.4 → 0.37 毫秒(只剩 1%)** | **就是格子 3,证明完毕** |

顺带把两个格子的贡献分开了:**格子 3 ≈ 30–37 毫秒(主因),格子 2 ≈ 持续存在的 6 毫秒**。

源码也印证了:`vllm/v1/core/encoder_cache_manager.py` 整个文件里,**搜不到 `cache_salt`**,它的索引只有 `mm_hash`(图片内容的哈希)。

---

## 6. 其他结论(一句话一条)

1. **文字信道是真的,而且超线性增长。** 共享前缀 16 → 4096 token,时间差 1.7 → **492.9 毫秒**(7.6 倍)。4096 token 时分布零重叠。
2. **`cache_salt` 关掉文字信道,而且租户内几乎免费。** 残余泄露在 1024–4096 token 时**小于 2 毫秒(≤1%)**;同一租户内部代价 ≤0.7 毫秒(就是噪声)。代价只落在"跨租户复用"上——**你只为本来就在泄露的那部分付钱**。
3. **我们的 oracle 比商业 API 干净得多。** 用论文自己的指标(AP):我们 **1.000**,论文在 17 家商业 API 上是 **0.71–0.90**。
4. **图片信道只认"完全一样"的图。** 改 1 个像素就认不出来了(差 0.14 毫秒)。所以只能确认"是不是这张图",不能模糊匹配。
5. **音频最不实用。** 连无损换格式(WAV → FLAC)都失效了——本地验证发现两者解码出的数组差 3.05e-05,已经足够改变索引。**攻击者必须持有完全相同的文件。**
6. **我们把密钥真的偷出来了,论文说他们做不到。** 论文原文:*"we were unable to reliably detect the presence of one additional cached token"*。我们端到端恢复了 3 个字段的模板化密钥:**18/18 全对,36 次查询搞定本来要 1728 次的空间(少 48 倍)**;开了 salt 就掉到随机水平(1/18)。
7. **负载下信道仍在,但更脆弱、不稳定。** 跑了两次,8–16 线程时结果不一致(一次完美分离,一次不能)。**能站住的说法是"存在但可靠性明显下降",不是"永远可分"。**

## 7. 这部分建议怎么讲(给 slide 用)

**如果只有一页:**

> 我们测了 vLLM 为防这类攻击而提供的 `cache_salt`。它对文本前缀缓存有效,但**对图片和音频无效**——因为一张图片在 vLLM 里会经过三个缓存,`cache_salt` 只保护了其中一个。攻击者用不同 salt 发同一张图,仍然快 **47 毫秒**,而且能 100% 区分。

**一句话版本:**

> 论文提出了"每用户缓存隔离"但从未验证;vLLM 实现了它;我们证明它对多模态不完整。

**可能要准备被问的问题:**

- *"为什么你们不用商业 API?"* → 复现那部分是队友做的。我们做扩展,而且自建实例让我们能拿到**白盒真相**(每个请求的缓存命中量),论文只能靠统计推断。
- *"47 毫秒够干什么?"* → 够做一个**零误判的存在性判断**:给我一张图,我能确定地告诉你"有人刚刚提交过这张完全一样的图"。
- *"这是不是只影响性能,不算安全问题?"* → 这是**隐私泄露**:泄露的是"另一个用户提交过什么内容",而且 vLLM 自己承认这个参数就是为了防这个。

## 7b. 我们做了重复性验证(K = 3,每次重启服务器)

因为**我们自己的一次运行曾经把结论翻转**,所以每条关键结论都重跑了 3 次,**每次重启 vLLM 服务器**:

| 结论 | 3 次的结果 |
|---|---|
| 文本 idle | AUC 0.000 ×3,AP 1.000 ×3,Δ 92.4 ± 1.0 ms |
| 文本 8 线程负载 | AUC 0.034 ± 0.017,AP 0.971 ± 0.015,Δ 55.1 ± 3.3 ms |
| 文本 salt ON(对照) | AUC 0.525 ± 0.041,AP 0.532 ± 0.018,Δ -0.1 ± 0.3 ms |
| **图像 salt-ON 攻击** | **AUC 0.000 ×3,AP 1.000 ×3,Δ 65.9 ± 0.7 ms** |
| 图像(同图不同提示词) | AUC 0.000 ×3,AP 1.000 ×3,Δ 66.1 ± 1.1 ms |
| 音频 salt-ON 攻击 | AUC 0.021 ± 0.036,AP 0.989 ± 0.019,Δ 57.2 ± 2.3 ms |
| FLAC 是否复用原始条目 | **3/3 全为 False** |

**好消息:可分性几乎完美可复现——所有头条结论都复现了。**

**要老实说的一点:绝对效应量跨会话会变。** 图像攻击最早测到 **46.7 毫秒**,这三次是 **65.9 毫秒**,差 **41%**。所以**效应量要报区间("约 47–67 毫秒"),不能报单点。**

## 8. 诚实的边界(被问到时不要回避)

- 每个模态只用了**一个模型**(3B/7B),每组 **12–60 次**;效应量很大(KS=1.0),结论不是边缘性的,但绝对延迟是硬件相关的。
- 多模态信道是**已知条目的"成员性判断"**,不是对未知图片的重建。
- 音频还需要**逐位相同的文件**。
- 恢复实验用的是**合成的模板化提示词**,不是真实的 system prompt。
- **我们只证明了缺陷,没证明修法。** 实现"给格子 2、3 加 salt"并证明信道关闭,是下一步。
- 负载下的可检测性**不稳定**。
