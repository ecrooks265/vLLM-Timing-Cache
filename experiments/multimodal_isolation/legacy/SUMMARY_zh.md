## 第一阶段:把 harness 修到能得出正确结论

接手时的 `modal_exp3_ttft.py` **跑不出它想跑的结论**。我找出并修了这些:

| # | 问题 | 后果 |
|---|---|---|
| 1 | **`cache_salt` 开启那一支是空的** —— "受害者"预热和"攻击者"探测用了**同一个 salt 字符串** | salt 开和关**逐位相同**,这个 harness **永远不可能**显示信道关闭。这是最致命的一个 |
| 2 | ground truth 是每个长度读一次**累计** gauge(而且该指标在 0.11.0 已废弃) | 无法知道**单个请求**是否命中 |
| 3 | 前缀是"N 个随机单词" | 既不是 N 个 token,也没对齐 block(block=16) |
| 4 | `pkill -f "vllm serve"` 可能静默失败 | 下一个服务器绑不上端口 |
| 5 | 镜像用 `Image.from_registry("vllm/vllm-openai")` | Modal 无法识别其中的 Python,直接报错 |
| 6 | `vllm==0.11.0` 会拉 transformers 5.x | 服务器启动即崩(tokenizer 报错) |
| 7 | 音频没装 `vllm[audio]` | 每个音频请求 HTTP 500 |

**修法**:每请求用引擎自己的计数器夹住(白盒 ground truth)、前缀通过服务器 `/tokenize` 校准到精确 token、明确 terminate 进程、pin transformers 4.55.2、装 audio extra。

**同时加了**:免费离线回归测试(`test_harness_offline.py`),包括对恢复逻辑的模拟验证。

---

## 第二阶段:跑完三个模态

在 Modal 上跑通了 **15 组实验**(L4 / A100,真 vLLM v0.11.0,真模型):

```
smoke → text → text2 → text_load → text_recovery
      → mm → mm_extra → mm_mechanism → mm_evict
      → audio → audio_extra
      → repeat_text → repeat_mm → repeat_audio
```

模型:`Qwen2.5-3B-Instruct`(文字)、`Qwen2.5-VL-3B-Instruct`(图片)、`Qwen2-Audio-7B-Instruct`(音频)。

**结果:发现了那个 headline** —— 防御对图片和音频无效。

---

## 第三阶段:证明"为什么"

不满足于"看起来是编码器缓存",做了三组对照:

1. 关掉 processor 缓存 → 优势**不变**(41.1 vs 42.5 ms)→ 不是它
2. 灌 400/1200 张图冲刷 → 效应**卡在 22% 不降** → 说明还有第二个冲不掉的
3. **关掉 processor + 冲刷** → **37.4 → 0.37 ms(残留 1%)** → 就是编码器缓存

---

## 第四阶段:补漏洞(三轮)

### 第一轮:严格统计
- 原来"信道关闭"是靠 p 值不显著 → 这是**absence of evidence**,会被审稿人打
- 改成 **bootstrap 置信区间 + 等价性上界**:1024–4096 token 时残余 **< 2 ms(≤1%)**

### 第二轮:补上缺失的攻击 + 边界
- **端到端恢复**(论文说他们做不到):18/18 字段,36 次查询 vs 1728
- 扩展到 **4096 token**:效应 86.9%(7.6 倍)
- **同图不同提示词**:攻击者不需要知道提示词
- **1 像素差异**:失效 → 限定在精确内容
- **FLAC/OGG/MP3**:连无损换容器都不行

### 第三轮:重复性
- 因为**我们自己的一次运行把结论翻转了**,所以每条结论**重启服务器跑 3 次**
- 结果:全部分离度复现;但发现**效应量跨会话会变 41%**

### 第四轮(进行中)
- 多重比较校正 ✅ 已完成(结果对我们有利)
- **patch vLLM 直接观测编码器缓存** ⏳ 补丁已写好,第一次跑发现插入位置错误,在修

## 我们主动纠正过的错误(这部分很重要)

**三个会伪造出"假泄露"的测量陷阱,每一个都先给出过一个又大又自信的错答案:**

| 陷阱 | 假结果 |
|---|---|
| chat template 是所有人共享的 → "全新前缀"其实会缓存 16 个 token | 所有断言 `cached==0` 的检查都是错的 |
| 攻击者 salt 没预热 → 顺序效应伪装成泄露 | 假的 `KS=0.433, p=0.007, AUC=0.748` |
| 攻击者命中**自己的**缓存 | 假的 54 ms "泄露";恢复实验因此 0/6 |

**另外我自己写错过两次结论:**
- 负载实验:先说"信道永远可分",后来发现两次运行不一致 → 改成"存在但可靠性下降" → K=3 后又修正为"下降约 40% 但仍强"
- 1 像素:先说"无法区分",其实 n=15 的置信区间包含 0.5 → 改成"上界 ~1.7 ms"
